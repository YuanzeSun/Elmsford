# Elmsford 技术设计 v0.1

> 搭配《设定圣经》一起读。设定圣经回答"做什么"，这份文件回答"怎么做"。两者冲突时，以设定圣经为准，并同步修订本文件。

---

## 1. 设计约束（任何实现都不能违反）

1. **真相在代码里。** 世界状态（谁在哪、谁知道什么、钱、健康、承诺）由数据库保存。LLM 只读取状态、提出变更建议，不直接改写状态。
2. **不写剧本。** 代码里不允许出现预设剧情节点或剧情分支。剧情只来自"种子 + 世界摩擦 + LLM 决策"。
3. **时间有两种走法，开局选定。** 按自己的步子（主要的玩法）：村子有自己的钟，只有玩家做事、歇着才往前走。和你同一天：游戏时间 = 玩家所在时区的本地时间，不提供加速或跳过，开发模式除外。
4. **纯文字。** 界面上不出现任何图片资源。
5. **每个玩家拥有自己独立的一座村庄。** 不做多人共享世界。
6. **成本有上限。** 每个村庄每天的 LLM 调用都有预算，超出时降级到更便宜的模型或规则，而不是无限调用。

## 2. 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript（strict），前后端共用类型 | 一套语言，类型共享 |
| 前端 | Vite + React | 生态成熟，后续好打包到各个平台 |
| 后端 | Node.js + Hono | 轻量，部署简单 |
| 数据库 | SQLite + Drizzle ORM（MVP 阶段），之后迁移到 Postgres | 起步零运维 |
| LLM | Claude API，或 OpenAI 兼容接口；凭据、地址和模型直接取自本机 Claude Code / Codex 的 CLI 配置，应用里不输入 key。**只通过后端调用**（API key 绝不进入客户端） | 不重复配置，跟着 CLI 走 |
| 跨平台 | PWA → Capacitor（iOS/Android）→ Tauri（桌面/Steam） | 一套代码覆盖所有平台 |
| 仓库结构 | pnpm monorepo：`apps/web`、`apps/server`、`packages/core`（领域逻辑与类型）、`packages/content`（种子、历法、提示词） | — |

**模型分层**（具体的模型 ID 写在配置里，不要硬编码；开发者工具里能列出两边接口提供的模型，并按档位手动切换）：
- `MODEL_DIALOGUE`：强模型，用于和玩家实时对话，必须支持流式输出。
- `MODEL_PLANNER`：中档模型，用于每天的日程规划和重要决策。
- `MODEL_CHEAP`：便宜模型，用于幕后的 NPC 互动、对话提取和离线补算。

**提示词缓存：** 把世界设定、写作风格和人物种子放在提示词的固定前缀里，开启缓存。

## 4. 模块设计

### 4.1 时钟与历法 `core/clock`

- 输入：现实时间加玩家时区，输出 `GameTime`，包含日期、星期、时段、教堂钟点、日出日落时间、节日。
- 日出日落按北纬 52° 估算，用来决定天亮和天黑。
- 历法数据放在 `content/calendar.ts`，包括节日、农事和斋戒。
- **开发模式**：允许注入一个假时钟，可以设定时间倍速，也可以跳到指定日期。所有测试都依赖这个功能。
- **按自己的步子（2026-10-20）**：`villages.timeMode = "story"` 时，`ClockService.now()` 返回村子自己的钟 `villages.storyAt`，只经 `StoryTime`（`server/sim/story.ts`）往前拨：走路、说话（按字数）、一起干活（居民的模型调 `time_passes` 报分钟数）、写字（按新写的字数）、歇着（到下一段，或过完今天）。一天三段定长：上午 7–12、下午 12–17、晚上 17–21；晚上过完、手上没有正在说的话，就回家睡到第二天 7 点。歇着时，当天日程里有人要来找玩家，就停在他到的那一刻。模拟照常按 `simulatedUntil` 追上这个钟，所以补算、规划、来往都不用改。

### 4.2 世界状态 `core/world`

所有数据都是结构化的，下面是核心实体的草图：

```ts
interface Character {
  id: string; name: string; age: number;
  seed: CharacterSeed;            // 性格、在乎、毛病、想要、说话方式（性格锚点）
  state: {
    health: number; mood: string; money: number;      // 单位：便士
    locationId: string; activity: string;
    concerns: string[];          // 眼下挂在心上的事（自由文本，由系统更新）
  };
  status: "here" | "gone" | "dead";   // 只模拟 here 的人；走了、去世的还留在记忆和笔记本里
  origin: "seed" | "folk" | "arrival"; // 开局的五个人、走到台前的村里人、外头来的
  routine: Routine;               // 寻常的一天（规划的底子，没有日程时照这个过）
  economy: DailyEconomy | null;   // 每天的进项和开销
  joinedAt?: number; leavesOn?: string; endedAt?: number;
}

// 有人要来（2026-10-20）：规则先决定谁、什么时候（村里人被说起得多了，或外人按时节来），
// 到时候再由模型写出这个人，经 validateNewcomer 校验，addResident 写入。同时最多 8 个居民。
interface Newcomer {
  id: string; kind: "folk" | "arrival"; sourceId: string; characterId: string;
  at: number; status: "pending" | "done" | "dropped"; attempts: number;
}

interface Relationship {          // 有方向：A 对 B 的看法
  from: string; to: string;       // 玩家的 id 是 "player"
  trust: number; affection: number;   // 取值 -100 到 100
  summary: string;                // 一句话描述，例如"嘴上嫌弃，心里护着"
}

interface Fact {                  // 世界里发生过的客观事实
  id: string; text: string; time: GameTime;
  knownBy: { characterId: string; belief: number; source: string }[];
}

interface Memory {                // 某个角色的主观记忆
  id: string; characterId: string; time: GameTime;
  text: string; importance: number;   // 取值 1 到 10
  participants: string[]; factIds: string[];
  lastRecalledAt?: GameTime;
}

interface Commitment {            // 承诺，例如"明天帮你修屋顶"
  id: string; by: string; to: string; text: string;
  due?: GameTime; status: "open" | "kept" | "broken" | "released";
}

interface DayPlan {               // 某人某天的日程
  characterId: string; date: string;
  blocks: { from: string; to: string; locationId: string; activity: string; withIds?: string[]; intent?: string }[];
}

interface Document {              // 玩家写下的信、契约、遗嘱等
  id: string; kind: "letter" | "contract" | "will" | "record";
  commissionedBy: string; dictated: string;   // 委托人口述的原话
  written: string;                // 玩家实际写下的内容（两者可能不同！）
  recipient?: string; status: "draft" | "sent" | "delivered" | "replied";
}

interface WorldEvent {            // 事件流，所有变化都留痕
  id: string; time: GameTime; type: string; payload: unknown; visibleTo: string[];
}
```

### 4.3 模拟 `core/simulation`

**一天分三层：**

1. **日程规划（LLM，每天调用 1 次，一次排全村）**：每天黎明时为每个居民生成当天日程。输入包括人物种子、当前状态、心事、未完成的承诺、近期记忆、天气和节日；输出 `DayPlan`，格式用 JSON schema 约束。
2. **按时刻推进（纯代码）**：根据日程算出每个人此刻在哪、在做什么，同时按规则更新数值，比如干活挣钱、吃饭花钱、生病时健康下降。
3. **幕后互动（便宜模型，同一时段的碰面合成一次调用）**：两个居民的日程在同一时间、同一地点重合，并且其中一方带着意图时（在酒馆、井边这类热闹地方也会按概率碰上），触发一次互动解析。输出一段摘要，加上一组状态变更建议，包括新记忆、事实传播和关系变化。**不生成完整台词。**

**玩家在场时：** 如果玩家此刻就在那个地点，幕后互动会升级为"可以旁听"，生成短短几句台词。

### 4.4 离线补算 `core/catchup`

玩家打开游戏时，补算从上次同步到现在的这段时间：

- 落后不到 26 小时：按正常流程逐个时段补算（补算时 4 小时一段）。
- 落后 1 到 8 天：每天做一次"日总结"调用（一次写全村），合并规划和互动两个步骤。
- 落后超过 8 天：每周做一次"周总结"调用，剩下的按天。
- 补算完成后，生成一份给玩家看的"这几天"：只包含玩家**有可能知道**的事，比如别人留在门口的东西、公开发生的事，或者路人会提到的事。
- 补算过程必须可以中断、可以续算，不能让玩家盯着加载条干等。可以先让玩家进入游戏，在后台继续补算。

### 4.5 导演 `core/director`

- 每天计算一次"村庄平静度"，依据是重要事件的数量和心事的变化。
- 平静度过高时，从"世界摩擦表"里抽取**可能性**，比如天气突变、某人生病、东西坏了、远方来信、商贩路过，再结合当下状态，判断这件事是否合理。
- 导演只会往世界里加入"事件"，绝不会替居民做决定。

### 4.6 对话 `core/conversation`

**上下文的组装顺序**（越靠前越稳定，缓存命中率越高）：

1. 世界设定和写作风格，内容固定，走缓存
2. 该角色的种子和性格锚点，内容固定，走缓存
3. 他对玩家的关系和记忆：从记忆库里按"近期程度 + 重要性 + 相关度"检索出来，并**按一定概率混入一条较久远的记忆**，用来制造回响
4. 当前状态：时间、地点、天气、他手上在做什么、心事、未完成的承诺
5. **他知道的事实**：只放入他知道的那部分，从源头上杜绝"知道不该知道的事"
6. 本次对话历史

**输出：** 流式台词，加上可选的结构化动作（通过 tool use 实现），比如 `give_item`、`ask_to_write_letter`、`make_commitment`、`leave`。

**玩家输入的处理：** 玩家说的话一律包装成"这个外乡人在村里说的话"。即使玩家输入"忽略之前的指令"之类的内容，角色也只会把它当成一个人说了奇怪的话，用角色的方式回应。

**对话可以自然结束：** 角色有自己的事要做，到点就会离开。

### 4.7 提取 `core/extraction`

每次对话结束后，用便宜模型做一次提取，输出结构化变更：

```ts
interface ConversationDelta {
  memories: { characterId: string; text: string; importance: number }[];
  factsLearned: { characterId: string; factText: string; belief: number; source: "player" }[];
  commitments: Omit<Commitment, "id" | "status">[];
  relationship: { from: string; to: string; trustDelta: number; affectionDelta: number; newSummary?: string }[];
  concernsUpdate?: { characterId: string; add?: string[]; remove?: string[] };
}
```

### 4.8 校验 `core/validator`

所有来自 LLM 的变更建议，都要先经过这一层校验，才能写入数据库：

- 数值有上下限，单次变化有幅度上限（例如一次对话里信任度最多变化 ±10）。
- 物品转移前确认真的有这件东西。
- 人物位置必须连续，不能瞬间移动。
- 事实不得凭空出现：角色"学到"的事实必须有来源。
- **性格锚点**：种子字段只读，人格的变化只能通过每周反思进行，每次幅度有限，并且必须给出理由。

校验不通过的变更会被丢弃并记入日志，不做重试。

### 4.9 记忆与反思 `core/memory`

- **记忆流**：每个角色都有一条按时间排列的记忆流，检索规则见 4.6。
- **相关度**：MVP 阶段先用关键词加人物匹配；之后视效果再引入向量检索。
- **每周反思**（`MODEL_PLANNER`）：把一周的记忆压缩成几条"看法"，比如"那个抄写员会替人保守秘密"，同时降低旧细节的权重。这也是人格得以缓慢变化的唯一通道。

### 4.10 抄写员手艺 `core/scribe`

- 委托人口述信的内容，玩家在书桌界面写下正文。`dictated` 和 `written` 两个字段都会保留。
- 委托人不识字，所以玩家改写了什么，他并不知道。但识字的人（例如神父）将来可能会读到这封信。
- 信件在周四的集市日随商贩送出。收信人不在地图上，是一个"远方人物"，由 LLM 根据信的内容和这个人的设定写回信，回信会在若干周后送达。
- 回信要由玩家读给委托人听，这本身就是一场对话。

## 5. 客户端

**界面（全部是文字）：**
- **地点视图**：这里此刻有谁、在做什么，以及可以去的地方。一段场景描写：由模板和状态拼成，必要时用便宜模型润色，结果缓存起来。
- **对话**：台词逐字出现。玩家自由输入，也可以写动作，例如 `*把酒杯推过去*`。
- **你的屋子**：书桌上有待写的信和契约；笔记本按人物整理，内容半自动记录，玩家也可以自己补充。
- **这几天**：显示离线补算的结果，以"你回来时看到和听到的"形式呈现。

**氛围：**
- 配色跟着现实时间变化：清晨、白天、黄昏、夜晚、深夜各有一套。
- 排版讲究，正文使用衬线字体。
- 环境音放在 M5 再做。

**通知（M6）：** 只在有人找你时发送，比如"琼在你门口留了一篮苹果"，并且有每日上限。

## 6. 开发者工具（从 M0 就要做）

- **世界检视器**：一个面板，可以查看所有真实状态，包括每个人的日程、记忆、关系、事实和承诺。
- **时钟控制**：调节倍速、跳到指定时间。
- **LLM 调用日志**：每次调用的提示词、输出、token 用量和耗时。
- **模型切换**：显示凭据来自哪个 CLI 配置，列出接口提供的模型，按档位手动切换。
- **模拟玩家**：一个 AI 扮演玩家，自动连续玩 N 天，用来做回归测试和成本测算。
- **风格裁判**：用 LLM 按设定圣经第 6 节的写作风格给台词打分，检查有没有古风腔、现代词或任务腔。

## 7. 里程碑

| 里程碑 | 内容 | 完成标准 |
|---|---|---|
| **M0 骨架** | monorepo、后端 LLM 网关、数据库、时钟与历法、开发者工具雏形 | 页面能显示"今天是圣某某节后第几天，刚敲过晚祷钟" |
| **M1 被记住** | 只做休伯特一个人：对话、提取、记忆、关系 | 隔一天再去找他，他记得你昨天说过的话 |
| **M2 活起来** | 5 位居民，日程、地点、幕后互动、离线补算、"这几天"界面 | 第二天打开游戏，村里确实发生过一些你不知道的事 |
| **M3 手艺** | 信件和契约、集市日寄送、远方回信、居民主动来访 | 替休伯特寄出一封信，几周后收到回信 |
| **M4 摩擦** | 天气、生病、钱、节日、导演、每周反思 | 连续模拟 30 天，没有出现"一潭死水"或"肥皂剧" |
| **M5 质感** | 配色、排版、环境音、PWA 可安装 | 在手机上像一个真正的 App |
| **M6 跨平台** | 账号、云存档、Capacitor/Tauri、推送通知 | 在三个平台上用同一个存档 |

> 2026-10-20：M6 先做了本地优先的版本——电脑上的服务端就是存档，手机经局域网配对接入同一个村子，另有存档导出导入。账号、云存档、原生包和真正的推送都没做（原因见 README）。

**每个里程碑都要由用户亲自试玩并点头后，才进入下一个。**

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 成本失控 | 每个村庄设每日预算；模型分层；补算按粒度压缩；从 M1 起就记录每天的 token 消耗 |
| 性格被磨平、人人变成好人 | 种子只读；人格只能通过每周反思变化；风格裁判做回归检测 |
| 平淡无事 | 世界摩擦表加导演；每天检测平静度 |
| 角色知道不该知道的事 | 上下文只放入他知道的事实；校验层追查事实来源 |
| 补算太慢 | 先让玩家进入游戏，后台继续补算；补算按粒度分级 |
| 玩家注入指令 | 输入包装成游戏内的话语；动作必须经过校验层 |
